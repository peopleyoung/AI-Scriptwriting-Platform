# 单进程回收站到期清理与 worker 恢复

状态：已确认，2026-10-13。明确平台以单进程、单 Uvicorn worker 部署，并据此约束回收站到期清理与生成任务的运行时补偿。

## 背景与决策

早期[开发设计](../development-design.md)设想 Redis/RQ 与多服务分离的 worker 拓扑。当前实现不依赖外部队列：生成队列保存在进程内存，数据库是唯一持久状态来源。任何依赖多副本共享内存或独立 worker 进程的设计都不能直接照搬，因此对「谁在什么时候清理到期回收站、进程重启后谁负责收口任务」给出单一负责人约定。

- **回收站到期清理**：移入回收站的作品在 `APP_TRASH_RETENTION_DAYS`（默认 30）天内可恢复；超过 `trashed_at + 保留期` 即视为到期，恢复请求返回 410 `TRASH_RETENTION_EXPIRED`。清理由应用进程自身承担：启动时先做一次到期清理，随后运行一个守护维护线程按周期扫描，避免为定时清理额外引入调度器。到期物理删除在一个显式事务内按外键依赖顺序逐作品删除其所有行（版本、发布、生成任务、导出、对话、提案、成员、活动锁等），并写入 `WORK_PERMANENTLY_DELETED` 审计。清理与恢复共享同一把进程内互斥锁，防止恢复与删除竞态。
- **worker 恢复**：进程启动在对外服务之前完成生成/对话状态补偿（详见 [ADR-0009](0009-work-input-lock-during-generation.md)），把重启遗留的 RUNNING/QUEUED 收口为确定终态、释放输入锁、清理孤儿锁，再按稳定顺序重新入队仍有效的排队任务。这样首个对外请求观察到的一定是已一致的状态。

## Consequences

- 单进程假设是显式契约：横向扩到多副本前，必须先把队列外置并为到期清理、状态补偿引入分布式协调，否则会重复清理或漏收口。
- 到期清理只在有进程存活时进行；进程长时间停机不会补齐错过的周期，但下次启动的开机清理会立即收敛到正确状态。
- 保留期天数经 `/api/v1/runtime-config` 暴露给前端，回收站与删除确认文案动态读取该值而非硬编码「30 天」，运维调整保留期后界面自动一致。
- 维护线程随应用优雅关闭：关闭信号置位后 join 有超时上限，不阻塞进程退出，也不在退出路径改写任务终态。
