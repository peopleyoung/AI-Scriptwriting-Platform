# 技术评审报告

日期：2026-10-10

评审对象：[产品规划](./product-plan.md)、[业务术语表](../GLOSSARY.md)及 ADR 0001–0005。

## 结论

**有条件通过，可以进入技术设计和基础工程搭建；不能直接进入完整功能开发或部署。**

产品边界已经足够支持首版拆分：内部团队、两种中文短剧模板、分阶段创作、作品授权协作、OpenAI 兼容接口与 Claude 原生接口、版本化生成、Docker Compose 部署。现有规划也正确地把平台管理员权限与作品内容权限分开。

开发前必须把下面的阻塞项写入接口、数据库约束和自动化测试。它们不是新增产品功能，而是把已确认的权限、版本和数据保护要求变成可验证的实现规则。

> **2026-10-24 漂移标注（当前实现基线）**
> 本报告保留 2026-10-10 的原始评审意见；实现术语、权限、外发门禁、密钥来源和部署形态已经变化。当前以代码为准：单进程 / 单 worker / 单实例；显式保存版本仅 OWNER，EDITOR 显式保存为产品待定项 pending；发布正式稿与创建导出仅 OWNER，导出下载要求 active 作品成员和未过期 token；回收站 30 天是恢复截止，永久清理仅管理员手动触发。以下在对应条目列出差异。

## Findings

### P1-1 作品授权还缺少可执行的资源边界

规划定义了管理员、所有者、编辑者和查看者，但没有明确每个 API 对 `work_id`、聊天、设定、版本、导出文件和回收站状态的统一授权入口。若只在页面隐藏按钮，管理员或已撤销成员仍可能通过接口读取内容。

**要求**：所有作品相关读取和写入先经过同一 `WorkAccessService`；权限判断同时检查成员状态、作品回收站状态和资源所属作品。管理员不设置绕过分支。所有权转移、邀请撤销和删除必须在事务内写审计记录。

> **漂移标注（2026-10-24）**：代码中没有 `WorkAccessService`，该名称仅为历史方案。统一入口实际为 `_require_work_member`（`app/main.py:444-468`），由 `_require` 包装复用（`app/features.py:295-296`）；它检查 ACCEPTED 成员状态、回收站可见性和角色集合，管理员没有作品授权绕过分支。作品永久清理当前由管理员手动端点执行（`app/features.py:1112-1124`），不是所有者删除接口。

### P1-2 生成任务、版本和并发编辑没有一致性规则

“每次生成形成版本”没有说明重复提交、网络重试、两个编辑者同时修改或恢复旧版本时的行为。直接重试会产生重复版本，恢复旧版本可能覆盖新内容。

**要求**：生成请求带幂等键；任务状态使用数据库状态机；作品内容采用乐观锁 `revision`；版本追加写入，恢复通过新版本表达，不删除历史版本。只有任务成功且输入版本仍满足预期时才能提交结果，否则标记冲突并要求用户重试。

> **漂移标注（2026-10-24）**：幂等键、数据库状态机、乐观锁和追加式版本已实现。生成请求使用 `idempotency_key` 与 `input_revision`（`app/features.py:742-792`）；冲突稳定错误码为 `REVISION_CONFLICT`，不是 `WORK_REVISION_CONFLICT`（`app/features.py:380-382,754-775`）。显式保存和恢复版本当前仅 OWNER 有入口（`app/features.py:391-443`）。

### P1-3 外发确认没有绑定具体数据范围和生命周期

目前只说“调用前确认”，没有定义确认是否适用于某个供应商、模型、作品版本、发送字段、时间范围，也没有撤销和供应商变更后的重新确认规则。

**要求**：确认记录绑定 `work_id + provider + model + data_classes + source_revision`，保存确认人和时间；供应商、模型、发送字段或作品设定发生变化时失效；所有者可撤销；没有有效确认时禁止创建外部生成任务。调用记录不得包含提示词和模型原文。

> **漂移标注（2026-10-24）**：逐次外发确认已由 [ADR-0011](./adr/0011-direct-model-configuration-and-member-invocation.md) 替代。当前没有 `external_consents` 的创建/撤销 API，ADR-0011 的直接成员调用路径不依赖逐次 consent；OWNER/EDITOR 按作品成员权限直接发起创作对话和生成。`external_consents` 历史表（`app/models.py:281-294`）、`GenerationJob.consent_id` 外键（`app/models.py:359`）及 consent 撤销、备份与恢复兼容逻辑仍保留，并在运行时被读取（`app/features.py:253-258`、`530-533`、`566-573`、`926`、`1066-1070`、`1105-1107`）。模型调用记录仍只保存元数据，不保存完整提示词和响应。

### P1-4 凭证、备份和回收站保护不足以验收

规划要求服务端加密凭证和 30 天备份，但没有定义主密钥来源、备份加密、恢复权限和回收站数据是否仍可被普通查询访问。

**要求**：主密钥由 Docker Secret 或等价的受控文件注入，不进入镜像、Git、日志或数据库；供应商密钥使用 AEAD 加密并只返回掩码；备份独立加密并限制到管理员/运维；回收站作品对普通业务查询不可见，恢复和永久删除均写审计记录。恢复演练必须验证权限和外发确认不会被错误恢复。

> **漂移标注（2026-10-24）**：当前主密钥来自 `APP_EXTERNAL_ENCRYPTION_KEY` 环境变量，而不是 Docker Secret。production 要求密钥稳定、至少 32 字符且非默认值（`app/config.py:22,34-37`）；模型凭证使用 AES-GCM 加密（`app/crypto.py:11-22`），轮换会破坏历史密文可解密性。回收站 30 天仅为恢复截止，超期后由管理员手动 `POST /api/v1/admin/trash/purge` 清理（`app/features.py:1112-1124`），没有自动删除定时任务。

## P2 风险

- **模型适配契约不完整**：两个供应商适配器需要统一流式输出、停止原因、token 用量、超时、重试、取消和错误分类；否则前端和计量逻辑会分叉。
- **模板演进可能污染作品**：作品创建时必须复制模板版本和参数快照；管理员更新模板不得改变已有作品。
- **导出对象未定义**：导出必须绑定不可变的正式稿版本，不能读取“当前草稿”拼装文件；DOCX 失败要留下可重试任务状态。
- **账号安全细节缺失**：需要 Argon2id、首次改密强制门禁、停用时撤销会话、登录限流、会话过期和管理员重置密码后的旧会话失效。
- **20 名并发没有容量策略**：需要生成任务并发上限、每用户/作品限流、队列积压可见性和外部供应商超时保护。
- **日志边界需要自动检查**：异常堆栈、HTTP 客户端 debug 和 worker 日志都可能意外打印 prompt 或响应，必须有脱敏测试。

> **漂移标注（2026-10-24）**：导出已绑定不可变发布记录（`app/features.py:874-896`）。当前 Markdown/DOCX 在创建导出时同步渲染并写入 `ExportJob.content`，表状态默认 `SUCCEEDED`（`app/models.py:372-385`），没有异步、失败重试或独立 DOCX 任务状态；渲染异常会使创建请求失败，因此上述“可重试任务状态”仍是未实现要求。

> **漂移标注（2026-10-24）**：并发与积压策略受单实例约束。后台生成是进程内单线程 + 内存队列（`app/worker.py:1-38`），同时最多一个生成任务；部署为单个 Uvicorn 进程（`Dockerfile:22-23`）。不能把“队列积压可见性”推导为 Redis/RQ 或独立 worker 服务，多实例化必须先设计外置队列和状态迁移。

## 建议采用的实现基线

详细方案见[开发设计文档](./development-design.md)。首版采用 React + TypeScript、FastAPI、PostgreSQL、Redis worker 和 Docker Compose；使用服务端 HttpOnly 会话、统一作品授权服务、追加式版本、幂等生成任务和独立模型适配器。该技术栈是无既有代码约束下的建议，不是已确认的产品需求。

> **漂移标注（2026-10-24）**：当前确实使用 React/TypeScript、FastAPI、PostgreSQL、HttpOnly Cookie、追加式版本、幂等生成任务和模型适配器；但“Redis worker”“统一作品授权服务”“六服务 Docker Compose”不是当前实现。实际为 `_require_work_member` / `_require`、进程内单线程 worker，Compose 仅 `db` 与 `app`（`docker-compose.yml:1-44`）。写操作还要求 CSRF，API 前缀为 `/api/v1`。

## 评审后的开发门禁

首轮代码合并前必须具备：

1. 未授权用户（包括管理员）无法通过 API 读取任何作品资源的测试。
2. 生成任务重复请求、并发修改、恢复和取消的状态机测试。
3. 外发确认失效、撤销、供应商/模型变更触发重新确认的测试。
4. 凭证不出现在数据库明文、日志、备份清单和 API 响应中的测试。
5. 模板版本快照、正式稿导出、回收站恢复/永久删除的测试。
6. Docker Compose 健康检查、迁移、备份恢复和最小权限配置的验收记录。

> **漂移标注（2026-10-24）**：第 3 项“外发确认失效/撤销”门禁已由 ADR-0011 替代，应改为验证成员直接调用、模型启停和同作品串行约束；第 6 项应按当前 `db` + `app` 双服务 Compose 验收，不得把六服务拓扑写成验收前提。回收站永久删除验收应对准管理员手动 purge 端点。

## 不属于本次阻塞项

公开注册、计费、多租户、Kubernetes、自动质量评估、复杂组织角色和跨作品检索已经明确暂缓，不应在首版任务中顺手引入。
