# AI 剧本写作平台首版规格

## Problem Statement

内部团队需要一个中文短剧创作平台，把用户与模型讨论形成的创作决定、人物、大纲和正文组织在同一部作品中。当前没有业务系统，创作资料、权限、模型外发授权、生成结果和正式稿之间没有可验证的统一边界。

平台必须同时解决几类风险：管理员的账号管理权限不能自动变成作品阅读权限；编辑者不能绕过作品所有者确认已确认设定或正式稿；模型调用不能在没有明确告知供应商、模型和数据范围的情况下外发作品内容；并发生成、版本恢复和回收站操作不能覆盖或泄露历史内容。

## Solution

构建一个面向个人或内部团队的中文短剧写作平台。平台角色分为管理员和普通用户，作品角色分为作品所有者、编辑者和查看者，两套角色彼此独立。作品默认私有，只有作品成员可以访问内容。

用户创建作品时选择版本化的剧本模板和作品参数。首版提供竖屏微短剧与网剧短剧模板，正文按集、场景、片段和结构化剧本块组织。创作简报、人物和故事大纲可以先编辑草稿，但必须依次由作品所有者确认；确认后的内容成为已确认设定，不能被临时指令直接覆盖。

平台保存一个可持久化的工作草稿。自动保存只更新草稿；显式正文保存、正文生成成功或恢复旧版本时，创建覆盖整部作品的不可变生成版本。生成集、场景或片段时，只替换目标范围并把其余内容带入新版本。作品所有者可以把任一版本发布为不可变正式稿，导出只接受正式稿发布记录。

任何创作对话或正文生成都必须使用作品所有者针对具体输入快照、模型配置版本和数据类别授予的外发确认。外发确认在输入快照、模型配置、数据类别变化或作品进入回收站后失效。模型配置版本不可变，供应商只有在管理员提供数据保留、删除和故障处理说明后才能启用。

首版使用 Docker Compose 单机部署，提供账号、作品与权限、模板与创作资料、异步生成、模型适配、版本与导出、备份与安全验收能力。规格通过一个最高层黑盒验收 seam 验证：从 API 边界执行完整创作生命周期，模型适配器使用可控测试替身，数据库、队列和文件存储使用真实组件。

## User Stories

1. 作为管理员，我想创建账号，使内部团队成员可以登录平台。
2. 作为管理员，我想停用和重新启用账号，使离开团队的账号不能继续访问平台。
3. 作为管理员，我想重置账号密码，使用户在忘记密码时可以恢复访问。
4. 作为新用户，我想使用一次性初始密码登录并被强制修改密码，使初始凭证不会长期有效。
5. 作为用户，我想使用账号密码登录和退出，使我的创作资料受到会话保护。
6. 作为管理员，我想维护已启用的模型供应商和模型配置，使团队可以选择允许使用的模型。
7. 作为管理员，我想轮换模型凭证而不暴露原始密钥，使供应商凭证可以安全维护。
8. 作为管理员，我想为供应商填写数据保留、删除和故障处理说明，使作品所有者在授权外发前能看到完整信息。
9. 作为管理员，我想查看账号、权限、模型配置、发布、导出、回收站和备份恢复的审计记录，使关键管理操作可追溯。
10. 作为普通用户，我想创建一部作品并自动成为作品所有者，使我可以开始创作。
11. 作为用户，我想在创建作品时选择竖屏微短剧或网剧短剧模板，使作品拥有明确的结构规则。
12. 作为用户，我想填写模板允许的集数、单集时长或字数、题材标签和输出格式，使作品参数符合创作目标。
13. 作为用户，我想让作品保存模板版本和参数快照，使管理员更新模板后不会改变已有作品。
14. 作为作品所有者，我想修改允许修改的作品参数，使创作方向可以在正文完成前调整。
15. 作为作品所有者，我想邀请查看者，使协作者可以阅读作品和创作记录。
16. 作为作品所有者，我想邀请编辑者，使协作者可以参与草稿创作和生成。
17. 作为受邀用户，我想在接受邀请前不能读取作品，使未确认的邀请不会泄露内容。
18. 作为作品所有者，我想撤销成员访问，使被撤销的成员立即失去访问权。
19. 作为作品所有者，我想在查看者和编辑者之间调整成员角色，使协作权限可以随团队分工变化。
20. 作为作品所有者，我想把所有权转移给已启用且已经是成员的用户，使作品不会因为账号变化而失去所有者。
21. 作为管理员，我想管理账号但不能绕过作品授权读取正文，使平台运维权与创作内容权保持分离。
22. 作为查看者，我想读取作品、创作对话、设定、大纲、正文、版本和正式稿，使我可以完整了解被授权的创作过程。
23. 作为编辑者，我想修改工作草稿，使我可以参与作品创作。
24. 作为编辑者，我想提交已确认设定的变更提案，使我可以提出新的创作方向而不直接破坏既有约束。
25. 作为编辑者，我想在已有有效外发确认时发起正文生成，使我可以推进被授权的创作任务。
26. 作为编辑者，我想在没有有效外发确认时只能准备生成请求而不能触发模型调用，使作品所有者始终控制外发授权。
27. 作为作品所有者，我想查看待审批的变更提案，使我可以决定哪些创作变化生效。
28. 作为作品所有者，我想按创作简报、人物、故事大纲的顺序确认创作阶段，使后续生成拥有完整且稳定的约束。
29. 作为作品所有者，我想拒绝或撤回变更提案，使未接受的设定不会影响后续生成。
30. 作为系统，我想在同一设定已有待审批提案时阻止第二个并行提案，使审批基础保持唯一。
31. 作为系统，我想在提案基础设定已经变化时报告冲突，使过期提案不能覆盖较新的确认结果。
32. 作为用户，我想在三阶段确认前与模型进行创作对话，使我可以探索主题、人物和故事方向。
33. 作为作品所有者，我想在每轮创作对话外发前看到供应商、模型配置版本和数据类别，使我能做出明确授权。
34. 作为用户，我想让创作对话保存为作品资料，使讨论过程可以被授权成员追溯。
35. 作为用户，我想让临时创作指令不能覆盖已确认设定，使故事基础不会被一次提示意外改变。
36. 作为作品所有者，我想在三阶段设定全部确认后生成正文，使正文建立在已接受的创作决策之上。
37. 作为用户，我想按集、场景或片段发起生成，使我可以逐步完成一部短剧。
38. 作为用户，我想在片段内进行连续选段重写，使我可以修订局部对白或动作。
39. 作为用户，我想看到生成任务的排队、运行、成功、失败和取消状态，使我知道创作操作是否完成。
40. 作为系统，我想限制同一作品同时只有一个运行中的正文生成任务，使并发结果不会自动覆盖或合并。
41. 作为用户，我想让瞬时错误和受控限流自动重试，使短暂的供应商故障不会立即中断创作。
42. 作为用户，我想让认证错误、参数错误和内容政策错误明确失败且不自动重试，使不可重试的问题可以被正确处理。
43. 作为系统，我想在取消、超时或结构校验失败时不产生生成版本，使版本历史不会包含半成品。
44. 作为用户，我想在显式保存正文时创建覆盖整部作品的不可变生成版本，使版本比较和恢复拥有完整上下文。
45. 作为用户，我想让自动保存只更新工作草稿而不制造版本，使版本历史保持有意义。
46. 作为作品所有者，我想比较生成版本，使我可以选择更合适的正文结果。
47. 作为作品所有者，我想恢复旧版本并生成一个新的版本，使历史记录不被覆盖。
48. 作为作品所有者，我想把任一生成版本发布为正式稿，使导出和交付使用明确确认过的内容。
49. 作为作品所有者，我想保留多个正式稿发布记录并标记当前正式稿，使不同交付版本可以追溯。
50. 作为作品所有者，我想导出 Markdown 正式稿，使我可以在纯文本工作流中交付剧本。
51. 作为作品所有者，我想导出 DOCX 正式稿，使我可以向需要文档格式的协作者交付剧本。
52. 作为系统，我想让导出只读取不可变正式稿，不读取当前工作草稿，使导出内容不会因未发布修改而变化。
53. 作为系统，我想让导出只包含完整剧本正文及必要标题、集和场景层级，不包含创作对话、待审批提案、模型调用记录或凭证，使交付内容保持清晰且安全。
54. 作为作品所有者，我想把作品放入回收站，使我可以先删除作品并在保留期内恢复。
55. 作为系统，我想让回收站作品对协作者和普通查询不可见，使被删除作品不会继续暴露。
56. 作为系统，我想在作品进入回收站时取消排队任务、请求取消运行任务并使外发确认失效，使删除后的作品不会继续外发或生成。
57. 作为作品所有者，我想在 30 天内恢复回收站作品，使误删作品可以找回。
58. 作为管理员或运维人员，我想从加密备份恢复数据库、作品文件和版本历史，使系统可以应对数据损坏。
59. 作为系统，我想让备份恢复不自动恢复运行中任务、外发确认或下载链接，使恢复后的运行状态需要重新验证。
60. 作为管理员或运维人员，我想运行健康检查、迁移、备份和恢复验证，使 Docker Compose 单机部署具备可重复验收路径。

## Implementation Decisions

- 采用账号平台角色与作品成员角色的双层权限模型。平台角色为 `ADMIN` 或 `WRITER`；作品成员角色为 `OWNER`、`EDITOR` 或 `VIEWER`。所有作品资源读取和写入统一经过作品访问服务，管理员没有隐含的作品读取分支。
- 采用单一作品模型表示完整中文短剧系列。正文结构为集、场景、片段和剧本块；片段是生成和重写的最小边界。首版支持场景说明、动作、人物和对白等结构化剧本块。
- 采用版本化剧本模板。首版提供竖屏微短剧和网剧短剧两种模板；模板定义创作简报、人物、大纲字段、正文结构、输出格式和校验规则。作品创建时复制模板版本和作品参数快照，既有作品不随模板更新改变。
- 采用阶段化创作决策。创作简报、人物和故事大纲可以并行编辑草稿，但只能按创作简报、人物、故事大纲的顺序确认。正文生成必须等待三个阶段均已确认。
- 采用变更提案管理已确认设定。临时创作指令不能覆盖已确认设定；同一设定只能有一个待审批提案；审批必须验证提案基础仍是当前确认结果，冲突时要求重新提交。
- 采用持久化工作草稿和追加式生成版本。自动保存只更新工作草稿；显式正文保存、生成成功和恢复操作创建覆盖整部作品的不可变版本。恢复旧版本通过新版本表达，不删除或更新历史版本。
- 采用正式稿发布记录。发布记录绑定不可变版本，一部作品可以保留多个发布记录并标记当前正式稿；导出只接受发布记录，不能从当前草稿拼装导出文件。
- 采用严格的外发确认生命周期。每次创作对话和正文生成都必须绑定作品、输入快照、模型配置版本和数据类别的有效外发确认。输入快照、模型配置、数据类别或作品回收站状态变化后确认失效。
- 采用不可变模型配置版本。管理员修改供应商、模型标识、接口参数或凭证引用时创建新版本；既有任务和授权继续绑定旧版本，新的调用使用新版本。原始凭证服务端加密保存，永不返回给普通用户。
- 供应商启用必须包含数据保留、删除和故障处理说明；作品所有者在授权外发前看到这些说明。平台不替外部供应商承诺其内部数据删除。
- 创作对话和正文生成使用不同的业务操作。创作对话保存讨论资料但不产生生成版本；正文生成任务成功后产生生成版本。两者都必须执行权限和外发确认检查。
- 生成任务采用 `QUEUED`、`RUNNING`、`SUCCEEDED`、`FAILED`、`CANCELED` 状态。同一作品同一时间只有一个运行中的正文生成任务；全局、用户、作品和供应商容量由管理员配置。
- 生成任务携带幂等键、输入版本、目标范围、模型配置版本和数据类别。重复幂等请求返回已有任务；输入版本在结果提交时发生冲突则任务失败且不产生孤立正文。
- 模型适配器统一支持流式与非流式响应、停止原因、用量、超时、取消和错误分类。仅对瞬时错误和受控限流自动重试；认证、参数和内容政策错误不自动重试。调用记录只保存供应商、模型、时间、状态、用量、耗时、错误代码和追踪 ID。
- 作品进入回收站后状态变为 `TRASHED`，普通查询和生成接口过滤回收站作品；排队任务取消、运行任务请求取消、外发确认失效。恢复回收站作品不会恢复原外发确认；超过 30 天后永久删除。
- 所有权只能转移给已启用且已经是作品成员的用户；原所有者转为编辑者。作品存在唯一所有者时，不能直接停用该所有者账号，必须先完成转移。
- 导出支持 Markdown 和 DOCX，两个格式从同一结构化正文渲染；下载地址短时有效并继承作品访问控制。
- API 采用稳定的版本化 JSON 契约和稳定错误代码。长任务只创建生成/导出任务，不在同步请求中等待模型完成。所有写操作使用乐观并发版本校验。
- 推荐实现基线为 React/TypeScript 前端、FastAPI/Pydantic API、PostgreSQL、Redis worker、受控文件存储和 Docker Compose；这些是实现基线，业务边界仍以本规格与 ADR 为准。
- 账号使用服务端会话、HttpOnly/Secure/SameSite Cookie、Argon2id 密码哈希、首次改密、停用/重置密码撤销会话、CSRF 防护和登录限流。具体时长和阈值作为安全配置参数。
- 每日备份数据库和作品文件，备份独立加密并保留 30 天；恢复需要管理员/运维权限和审计记录，备份目录不能作为应用可写目录。
- 首版只验收 Docker Compose 单机、本地或已明确主机上的健康检查、迁移、备份恢复和安全配置；没有真实生产参数时不宣称完成生产部署。

## Testing Decisions

- 测试以外部可观察行为为准，优先验证 API 返回、权限结果、状态变化、版本内容、导出产物和审计边界，不测试具体类层次、数据库表实现或 UI 按钮隐藏。
- 使用一个最高层黑盒验收 seam 覆盖完整生命周期：创建账号 → 首次改密 → 创建作品 → 邀请成员 → 三阶段确认 → 外发确认 → 创作对话 → 分段生成 → 版本比较/恢复 → 正式稿发布 → Markdown/DOCX 导出 → 回收站恢复。
- 在模型适配器边界使用可控测试替身验证 OpenAI 兼容和 Anthropic 适配器的最小请求、流式响应、停止原因、用量、取消、超时和错误分类；不向真实供应商发送测试作品内容。
- 验证每个平台角色与作品成员角色的允许/拒绝矩阵，包括管理员无授权读取作品返回拒绝、查看者不能修改、编辑者不能审批/发布/恢复/导出、所有者可以执行所有作品操作。
- 验证外发确认绑定输入快照、模型配置版本和数据类别；输入版本、模型版本、数据类别变化、所有者撤销或回收站操作后必须拒绝新的外部调用。
- 验证模板版本快照和作品参数隔离：管理员发布新模板不改变已有作品，作品只能使用模板允许的字段和范围。
- 验证工作草稿与生成版本边界：自动保存不产生版本，显式保存/生成/恢复产生整部作品版本，恢复不删除历史，正式稿发布绑定不可变版本。
- 验证生成任务状态机、幂等键、同作品串行限制、队列容量、瞬时错误重试、不可重试错误、取消和 worker 租约恢复；任何失败或取消不得产生孤立正文版本。
- 验证并发编辑和乐观锁：两个编辑者同时写入、提案基础变更、生成结果提交时输入版本变化，都应返回稳定冲突结果并保留已存在版本。
- 验证日志、审计记录、错误响应、备份清单和模型调用记录不包含完整提示词、模型原文、作品正文或供应商密钥。
- 验证回收站隔离、30 天清理、恢复、永久删除、任务取消和外发确认失效；恢复操作不得复活原任务、授权或下载链接。
- 验证备份恢复能恢复数据库、作品文件和版本历史的一致状态，并验证恢复权限、审计记录和最小权限配置。
- 当前仓库没有既有业务测试可复用；测试应以开发设计中规定的权限矩阵、状态机、供应商契约测试和端到端流程作为测试先例。

## Out of Scope

- 公开注册、计费、多租户隔离和复杂组织架构。
- Kubernetes、多节点弹性部署、生产域名和未明确的真实部署主机参数。
- 自动剧本质量评估、自动发布、无审批批量改写和模型自主修改已确认设定。
- 跨作品检索、复杂自定义角色、跨作品成员继承和管理员隐式应急阅读权限。
- 外部 Markdown、DOCX 或其他剧本文件导入。
- 跨片段任意文本范围重写；首版重写不跨越片段边界。
- 让模型调用记录保存完整提示词或模型原文。
- 由平台保证外部供应商内部的数据保留或删除行为。
- 在没有生产参数和明确授权时创建或派发 AutoWonder 首单、合并代码或宣称完成生产部署。
- 把安全时长、队列数值、具体模板默认数值和供应商费用策略固化为不可变业务语义；这些属于可配置的实现参数。

## Further Notes

- 本规格基于已确认的产品规划、技术评审、开发设计、术语表和 ADR 0002、0003、0004、0006 综合形成。
- 规格使用 `管理员`、`普通用户`、`作品`、`作品所有者`、`编辑者`、`查看者`、`创作简报`、`已确认设定`、`变更提案`、`工作草稿`、`生成版本`、`创作对话`、`外发确认`、`剧本发布`、`生成任务` 等术语，不引入同义替代词。
- 首版开发应按基础工程、认证与审计、作品与权限、模板与创作资料、版本与生成任务、模型适配与外发确认、协作工作区与导出、备份安全与验收的顺序执行。
- 本规格发布为本地 issue tracker 中的 `ready-for-agent` 规格；实现前仍需确保产品规划和开发设计文档与本规格保持一致。
